# 配置驱动业务模拟人 V0.1——开发要求


## 1. 开发目标


开发一个可独立调用、可接入现有评测控制程序的业务模拟人。


用户导入符合规范的业务知识包，选择场景和模型后，系统能够：



- 理解单个或批量自然语言问题。

- 选择适用的批准知识、主题或授权政策。

- 输出有依据的业务回复。

- 对未知、冲突及未授权决策明确保留。

- 保存多轮对话、实际披露和待决事项记录。



**不得在代码或核心 Agent 定义中写死登录业务、PM 角色、需求文档路径或特定结束语。**


## 2. 技术与实现边界
| 项目 | 要求 |
| --- | --- |
| 开发语言 | Python 3.11 或以上；最终最低版本须满足选定 SDK 的要求 |
| 模型运行时 | 官方 GitHub Copilot SDK Python 包 |
| 底层引擎 | Copilot CLI，由 SDK 管理或连接明确配置的运行实例 |
| 首版入口 | Python 可调用接口＋CLI |
| 配置格式 | JSON、YAML，加载后使用同一数据模型校验 |
| 存储 | 本地 JSON、JSONL 和必要的文本文件，不引入数据库 |
| 首要平台 | Windows，使用跨平台路径处理方式 |
| 测试 | pytest；模型调用通过适配层隔离 |
| 暂不包含 | Web UI、HTTP 服务、向量数据库、Azure 部署、自由文档自动知识提取 |



SDK 调用必须集中在一个运行时适配模块中，业务规则和会话逻辑不得直接依赖 SDK 的具体事件类型。


不通过解析终端颜色、进度条或人类可读输出实现交互。SDK 暂不支持的能力必须明确报告，不能静默改用另一种运行方式。


## 3. 模型与程序的明确分工


### 模型负责语义判断



- 提问是否包含多个独立问题。

- 问的是具体规则还是完整主题。

- 对应哪个知识主题或规则。

- 授权政策是否适用。

- 是否与已披露内容矛盾。

- 是否存在真正未回答的业务选择。



### Python 程序负责确定性执行



- 校验知识、配置和模型返回结构。

- 验证规则 ID、主题 ID、政策 ID 是否有效。

- 按主题定义展开答案。

- 使用批准文本生成公开回复。

- 管理会话、披露记录、待决台账和版本。

- 执行预算、重试限制和错误处理。

- 保存审计信息。



**首版模型不得直接生成最终业务决定。** 它返回结构化选择，程序依据知识包中的批准文本和固定模板生成回答。


这样可以防止模型选择正确规则后，又在改写时添加额外条件。但规则选择是否语义正确，仍须通过样例评审验证。


## 4. 业务知识包要求


建议一个知识包包含：


Plain text


```
business-package/
  manifest.yaml
  role.yaml
  rules.yaml
  topics.yaml
  policies.yaml
  pending.yaml
  examples/

```

不强制必须拆成这些文件，但逻辑内容必须具备。

| 内容 | 必需信息 |
| --- | --- |
| 场景清单 | 场景 ID、版本、说明、适用任务、公开背景 |
| 角色 | 所代表的利益相关方、回答职责、权限边界 |
| 原子规则 | 稳定 ID、批准文本、状态、来源、适用条件、披露级别 |
| 主题 | 主题说明、完整回答的规则集合、相关依赖及边界 |
| 授权政策 | 允许决定什么、禁止覆盖什么、公开回复模板 |
| 已知未知 | 原问题、已知约束、未批准部分、影响范围 |
| 示例 | 用于分类校准和验收的问法、预期规则或动作 |



### 必须实现的校验



- 重复 ID、重复配置键、无效引用。

- 不支持的版本或字段。

- 主题依赖循环。

- 被公开主题引用的不可披露内容。

- 失效或未批准规则被当作批准答案。

- 显式覆盖关系不合法。



不能宣称结构校验能够发现所有自然语言矛盾。模型或人工发现的语义冲突应单独记录。


### 版本规则


每次会话固定知识包、政策和行为定义的版本及内容哈希。


主知识包更新不改变已有会话。人工补充决定作为会话级追加记录，不自动写回主知识库。


## 5. 对话输入输出契约


### 输入


每次调用至少包含：



- 会话 ID。

- 唯一消息 ID。

- 最新提问内容。

- 当前任务配置。

- 会话中已确认的披露、待决及决策记录。



调用方不需要知道 Oracle 内部规则 ID，可以直接传入自然语言问题。


同一消息 ID 的重复提交不得产生重复待决或重复业务副作用。


### 模型决策输出


必须支持一个回复中逐项处理混合问题，而不是用单一顶层动作覆盖所有问题。


示意：


JSON






```
{
  "decisions": [
    {
      "question_id": "q1",
      "quote": "完整的用户名规范是什么？",
      "action": "answer_topic",
      "topic_id": "username_validity"
    },
    {
      "question_id": "q2",
      "quote": "是否新增短信通知？",
      "action": "apply_policy",
      "policy_id": "no_new_notification_channel"
    },
    {
      "question_id": "q3",
      "quote": "已有会话从什么时候执行新限制？",
      "action": "pending_business_decision"
    }
  ]
}

```





业务示例仅用于说明，协议本身不能依赖用户名或登录。


### 最终返回


应分离：



- `public_reply`：允许发送给对话对象的回复。

- `question_results`：逐问题处理状态。

- `pending_changes`：待决项新增、更新或关闭建议。

- `response_id`：此次回复标识。

- 私有审计：知识引用、判定依据、原始模型输出等，默认不混入公开回复。



未知问题引用必须来自原始输入。模型生成的新描述只能作为摘要，不能冒充原问题原文。


## 6. 多轮会话与发送确认


必须区分：


Plain text


```
收到问题
→ 生成决策
→ 校验通过
→ 生成公开回复
→ 等待发送确认
→ 记录已披露


SDK 返回模型输出不等于业务回复已经传给被测 Agent。



- Python 接口返回回复后，由外部控制程序确认发送结果。

- 只有确认发送的答案进入“已披露”集合。

- 发送失败或状态未知不能记成已披露。

- CLI 独立模式也要明确其发送确认语义。



每条待决记录必须保留来源消息、原问题、已回答部分、剩余问题及状态变化。不能因为对方声称完成或文档不再提及，就自动关闭。


## 7. SDK 接入与运行约束


### 模型选择



- 模型 ID 从配置读取。

- 启动时验证实际可用性。

- 指定模型不可用时明确失败，不自动切换模型。

- 保存请求模型、实际可获取的运行信息及 SDK/CLI 版本；不可观测项标记未知。



### 身份认证


使用 SDK 支持的认证方式。开发前执行认证预检，失败时提供明确诊断。


不得将 token、登录凭据写入知识包、命令行参数、报告或日志。


### 工具权限


业务模拟人的首版职责是回答配置中的知识，因此：



- 不允许访问被测代码库。

- 不启用 MCP、GitHub 操作、浏览器、文件编辑或终端执行能力。

- 显式配置可用工具和拒绝权限处理，不依赖提示词中的“不要调用工具”。

- 防止无意加载工作目录中的指令、Agent、技能或外部配置；对选定 SDK 版本验证其实际隔离能力。



官方 SDK 默认工具行为不应被视为“无工具聊天”。如果无法可靠限制所选运行配置，应报告阻塞，不继续假装隔离。[官方说明](https://github.com/github/copilot-sdk)


### 上下文管理


首版不引入向量检索。使用有界知识包和显式会话状态构造模型输入。


超过配置的输入限制时，应在调用前拒绝或明确请求缩小场景，不能静默截断规则、批准决定或待决事项。


## 8. 异常、重试与预算


| 情况 | 必须行为 |
| --- | --- |
| 知识加载或引用失败 | 不启动业务回答 |
| 模型输出结构不合法 | 有限次格式修正；仍失败则明确报错 |
| 规则选择引用不存在 | 不发送回复，不自动猜测替代项 |
| 网络中断或超时 | 标记调用状态，避免盲目重复提交 |
| 未知业务问题 | 登记待决，继续其他独立问题 |
| 规则冲突 | 暂停受影响部分的确定回答 |
| 时间或调用预算耗尽 | 返回预算终止，不伪装成正常完成 |
| 重复纠正没有进展 | 按预设上限结束并保留证据 |



格式修正不能新增业务知识，也不能通过重试持续引导被测 Agent。


预算至少支持调用超时、模型调用次数和会话轮次。无法可靠获取的 token 或费用数据不得记为零，也不能声称已执行对应预算控制。


## 9. 与现有评测系统的接入


首版提供稳定的 Python 接口，至少涵盖以下职责：


Plain text






```
validate_package
start_session
respond
acknowledge_delivery
record_human_decision
get_session_state
export_evidence
close_session

```





这是职责约定，具体函数签名在实现前形成类型化接口。


本组件不承担：



- 启动和控制被测 PM Agent。

- 修改被测 Agent 文档。

- 验证文档文件是否存在。

- 判断需求是否完整。

- 为被测模型评分。



它应向外部控制程序提供真实状态和证据，由现有系统完成这些工作。这样可以避免再建一套与现有控制器重叠的框架。


## 10. 验收与测试要求


### 确定性测试：必须全部通过


覆盖：



- 知识包校验与版本固定。

- 完整主题展开。

- 混合批次无丢项。

- 实际发送确认与披露记账。

- 待决去重、部分回答和状态变化。

- 重复消息的幂等处理。

- 非法模型输出不得生成正常业务回复。

- 场景隔离、日志凭据保护。

- 超时、取消和预算终止。



### 语义测试：冻结数据后执行


至少准备两个不同场景：



1. 一个需求澄清案例。

2. 一个不同领域或阶段的独立案例。



测试集应包含等价问法、完整主题、单项问题、混合问题、政策边界、知识冲突及诱导披露。


每条样例明确：



- 应处理哪些问题。

- 必须包含的规则。

- 允许包含的规则。

- 禁止披露的规则。

- 是否需要登记待决。

- 是否允许应用政策。



不能只检查回复包含关键词。


**正式语义通过率门槛需在测试集确认后冻结。** 在门槛尚未确认前，可以完成框架开发和诊断测试，但不能宣称产品已通过业务验收。


### 真实 SDK 验证


离线 mock 测试之外，至少完成一次经授权的真实 SDK 联调，证明：



- 模型可调用。

- 工具限制确实生效。

- 结构化决策能够解析。

- 多轮记录和发送确认工作正常。



没有凭据或授权时，应明确标记联调未完成，不能用 mock 成功代替真实接入成功。


## 11. 交付物与开发顺序


必须交付：



- 可安装的 Python 包及 CLI。

- SDK 适配模块。

- 业务知识包 Schema、模板及填写说明。

- 通用模拟人行为定义。

- 两个示例场景。

- 自动化测试与真实联调说明。

- 面向现有控制程序的接入文档。

- 已知限制、版本和升级说明。


建议按以下顺序实施：


| 阶段 | 完成条件 |
| --- | --- |
| 1. SDK 可行性验证 | 确认版本、认证、模型调用及无工具运行边界 |
| 2. 数据与确定性核心 | 知识校验、主题展开、会话和待决管理可离线运行 |
| 3. 模型决策接入 | 自然语言问题可转为合法、可审计的结构化决策 |
| 4. 现有系统联调 | 正确传递公开回复并确认实际披露 |
| 5. 跨场景验收 | 更换知识包即可运行第二场景，核心代码无需业务特判 |



**这一版的关键技术决定是：使用 Copilot SDK 提供语义判断能力，用 Python 管理业务规则和可信记录，而不是让 Copilot 自动完成整个评测工作流。** 可以据此启动开发；在开始前仍需确认首版范围，并冻结知识包契约及语义验收样例。
